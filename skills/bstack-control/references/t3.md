# T3 Code mechanics for coordinators

This file holds how a coordinator uses T3 Code's project, thread, pending-request, and
scheduling tools. Unlike `delegate_task` (used for short-lived subtasks and reviews),
coordinator-dispatched **work sessions** are top-level threads created with
`t3_thread_launch`, because the owner works with them directly.

## Tool access and thread links

- **MCP tools and late loading:** T3 Code exposes its tools directly via MCP. Because T3
  tools can load late, try calling a tool once before treating it as absent.
- **ACP fallback:** if a T3 tool is absent from the harness's MCP tool list (or excluded
  by schema filtering) while `T3_ACP_MCP_NODE` is set, call it through the terminal:

  ```sh
  ELECTRON_RUN_AS_NODE=1 "$T3_ACP_MCP_NODE" ${T3_ACP_MCP_ENTRYPOINT:+"$T3_ACP_MCP_ENTRYPOINT"} acp-mcp-call <tool-name> '<json-args>'
  ```

- **Thread links:** whenever you mention a thread to the owner (in a recap, pointer, or
  handover), cite it by the verbatim `link` returned by `t3_thread_launch`,
  `t3_thread_list`, or `t3_thread_read` rather than a plain title or bare ID.

## Ensure the project is registered

Each `control` project (`<project>_workspace/<project>`) and the `chief-workspace/`
directory live as registered T3 Code projects so their threads stay grouped in the
sidebar:

1. Call `t3_project_list` and match by `workspaceRoot`.
2. If the directory is not registered yet, register it with `t3_project_create` passing
   `title` (`<project>` or `chief`) and `workspaceRoot` (the absolute path of the main
   checkout or `chief-workspace`).

## Resolve model selection

Call `orchestrator_capabilities` once per coordinator thread before launching the first
session (and again only after an error or when the owner changes provider settings). Use
the live response as the authority for exact `providerInstanceId`, `model` IDs, and
option keys:

| Runner | `providerInstanceId` | Typical effort option key |
| --- | --- | --- |
| Claude Code | `claudeAgent` | `effort` |
| Codex | `codex` | `reasoningEffort` |
| `agy` (Antigravity) | `antigravity` | `thought_level` |
| Cursor CLI | `cursor` | `effort` or `reasoning_effort` (check per model) |
| `pi` | `pi` | `thinking` (model ID `<provider>/<id>`) |

If a confirmed provider or model is disabled or unavailable in `orchestrator_capabilities`,
report it and stop for the owner; never substitute silently.

## Open a work session

1. **Prepare the directory first** (see [sessions.md](sessions.md), "Dispatch", step 2):
   - *Control session:* create `<project>_workspace/worktrees/<name>` with
     `git worktree add` and symlink gitignored `AGENTS.local.md` from the main checkout.
   - *Chief-of-staff:* create `work/<name>/` inside `chief-workspace/`.
2. **Write the brief** to `briefs/<name>.md` from [work-brief.md](work-brief.md).
3. **Launch the top-level thread** with `t3_thread_launch`:
   - `title`: `<name>` (or `<name>: <short summary>`).
   - `projectId`: the project's ID (omit to inherit when launching inside the same project).
   - `modelSelection`: `{ provider, instanceId, model, options }` matching the owner's
     confirmed runner, model, and effort from `orchestrator_capabilities`.
   - `workspaceStrategy`:
     - *Control session:* `{ type: "existing_worktree", worktreePath: "<abs path to ../worktrees/<name>>" }`.
     - *Chief-of-staff:* `{ type: "root" }` (the thread runs in `chief-workspace/`, and
       the brief directs its notes and outputs to `work/<name>/`).
   - `message`: if `AGENTS.local.md` names a first instruction for new sessions, include it
     or note it first, followed by `"Read <abs brief path> and follow it."`
   - `clientRequestId`: a stable key so a retry after a transient failure does not create a
     duplicate thread.
4. **Record and hand over.** Record the returned `threadId` and verbatim `link` in
   `status.md`, and hand the verbatim `link` to the owner.

Do not launch work sessions with `delegate_task` (those are child threads without normal
owner-driven handoff) and do not pass `workspaceStrategy: { type: "worktree" }` unless the
owner explicitly opts out of the `<project>_workspace/worktrees/` layout.

## Open a coordinator

Inputs: the directory (a project's main checkout or `chief-workspace/`), the project title
(`<project>` or `chief`), the thread title (`<project>-control` or `chief`), the role
argument (`control` or `chief`), and the runner and model the owner chooses for the
coordinator.

1. **Check for a live one.** Ensure the target directory is registered (`t3_project_list` /
   `t3_project_create`), then call `t3_thread_list` for that `projectId`. If an active
   (non-archived) coordinator thread for that role already exists, report its verbatim
   `link` and stop; one coordinator per project, and one chief.
2. **Launch the thread.** Call `t3_thread_launch` with `projectId`, `title`,
   `workspaceStrategy: { type: "root" }`, the owner's chosen `modelSelection` (ask if not
   yet stated; `bstack-control` imposes no coordinator model or tier rule), and `message`
   invoking `bstack-control` (such as `/bstack-control <role>` or, in `pi`,
   `/skill:bstack-control <role>`, preceded by any first-session preference from
   `AGENTS.local.md`).
3. **Hand over.** Give the owner the new coordinator thread's verbatim `link`. Your part
   ends there; this thread keeps its own role.

## Inspect live state

T3 Code replaces terminal screen-reading with structured thread queries:

1. **List threads:**
   - *Control session:* `t3_thread_list` for this project (leave `includeSubagents` unset or
     `false` so `delegate_task` child threads opened by work sessions stay out of top-level
     rows).
   - *Chief-of-staff:* `t3_thread_list` with `allProjects: true` to inspect project control
     threads, project work threads, and your own outside work threads.
2. **Check pending user questions:** for each tracked active thread, call
   `t3_pending_request` with `action: "list"` and `threadId`. Any listed request means the
   thread is waiting on the owner's answer (note: permission approvals are not listed here,
   so check thread status and recent messages too). Never call `action: "respond"` unless
   the owner explicitly asks you to answer on their behalf.
3. **Read recent messages when needed:** call `t3_thread_read` (`threadId`, `view: "messages"`,
   small `limit` such as `5`) to check whether the latest assistant reply asks the owner
   for a decision, reports an unrecoverable failure, or is waiting on CI / external review.
   Use this only to classify state and write a one-line pointer; take work conclusions and
   progress from repository files and git history.

## Pass a message from the owner

Only when the owner explicitly asks you to forward a message to a work session: call
`t3_thread_send` with `threadId`, `message` (the owner's words unchanged), and
`mode: "auto"`. Never send messages to project control sessions from `chief`, and never
answer a work session's question without the owner's explicit instruction.

## Periodic refresh (opt-in)

T3 Code does not provide a multi-thread background wait loop for top-level threads
(`t3_thread_wait` waits synchronously on a single thread and blocks the current turn). Do
not poll with `t3_thread_wait` or shell `sleep`.

By default, coordinators in T3 Code run in **pull mode**: refresh whenever the owner sends
a message or asks for a recap.

Only when the owner explicitly asks for background periodic refresh:

1. Call `list_scheduled_tasks` first to confirm no refresh task is already scheduled for
   this thread (avoid duplicates).
2. Create one with `schedule_task`:
   - `title`: `<project>-control refresh` (or `chief refresh`).
   - `prompt`: `"Refresh the bstack-control status"` (tell the owner only when the refresh
     finds something new under Needs you or Overlaps; otherwise update `status.md`
     silently).
   - `schedule`: `{ type: "interval", everyMs: 1800000 }` (30 minutes, or the interval the
     owner requests).
   - `bindToCurrentThread: true`, `enabled: true`.
3. Remind the owner that T3 Code scheduled tasks persist across restarts until paused
   (`schedule_task` with `scheduledTaskId` and `enabled: false`) or removed
   (`delete_scheduled_task`). Offer to pause or delete the task when wrapping up a
   coordinator.

## Close a work session

On the owner's permission only, and only for a top-level work thread you created:

1. If the thread is still running (`running`, `starting`, or `queued`), stop its active turn
   with `t3_thread_interrupt` (`threadId`, `stop: true`). Never call `t3_thread_interrupt`
   on a `delegate_task` child thread.
2. Archive the thread with `t3_thread_organize` (`threadId`, `action: "archive"`). This
   removes it from the active sidebar while keeping its history recoverable via
   `unarchive`.
3. If the owner instead asks to mark a thread finished while keeping it visible under
   settled threads, use `t3_thread_organize` (`threadId`, `action: "settle"`).

Child threads that a work session created itself via `delegate_task` belong to that work
session; leave them alone unless the owner says otherwise.
